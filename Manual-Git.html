La terminal y tu carpeta: dónde se escriben los comandos

Los comandos git … se escriben en una terminal, no en el navegador ni en GitHub. La terminal siempre está «parada» en una carpeta, y Git trabaja sobre la carpeta donde está parada.

1. Abre la terminal

  • En VS Code: menú Terminal → New Terminal (o View → Terminal). Se abre parada en la carpeta que tienes abierta. Tu atajo está en el capítulo 9 (Ctrl + ñ).
  • Fuera de VS Code sirve cualquier terminal (Git Bash, PowerShell…) donde git --version responda.

Fuente oficial: VS Code · La terminal integrada

Las rutas, las fechas y los códigos de ejemplo están reemplazados: en tu computadora verás los tuyos.

3. ¿Estoy dentro de un proyecto Git?

Escribe git status. Git sube por las carpetas hasta encontrar la carpeta oculta .git: por eso funciona en cualquier subcarpeta del proyecto y falla fuera de él.

Estados de Git: cómo leer git status

git status es el tablero de Git: dice en qué estado está cada archivo y cómo va tu rama frente al remoto. Aquí está cada estado, qué significa y qué comando lo cambia.

1. El ciclo de vida de un archivo

  1. Sin seguimiento

    En git status: Untracked files: · corto: ??

    Archivo nuevo: Git todavía no lo conoce.

    Sale con git add

  2. Modificado (rojo)

    En git status: Changes not staged for commit: · corto: M

    Cambió en tu carpeta, pero todavía no pasó por git add.

    Sale con git add (o se descarta con git restore)

  3. Preparado (verde)

    En git status: Changes to be committed: · corto: M o A

    Listo para entrar en el próximo commit.

    Sale con git commit (o vuelve atrás con git restore --staged)

  4. Confirmado

    Ya no aparece como archivo en git status; está en git log.

    Guardado en tu historial local. Si tu rama tiene remoto, git status dice «ahead of … by N commits».

    Sale con git push

  5. Subido

    En git status: Your branch is up to date with 'origin/…'

    Está también en el remoto (según el último fetch o pull).

    El equipo lo recibe con git pull

2. Los códigos cortos de git status -s

Dos columnas: la izquierda es el staging (preparado) y la derecha es tu carpeta de trabajo. Fuente: git-scm.com · git status.

CódigoSignificaSalida real
??Archivo nuevo sin seguimiento?? login.js
MModificado en la carpeta, sin preparar M LEEME.txt
M Modificado y preparadoM README.md
A Archivo nuevo ya preparadoA login.js
UUSin fusionar: ambos lo modificaron (conflicto)UU README.md

3. Cómo va tu rama frente al remoto

Al día

Tu rama y la remota apuntan al mismo commit. No hay nada que subir ni que bajar.

Por delante (ahead)

Tienes commits locales que no subiste. Siguiente paso: git push.

Por detrás (behind)

El remoto tiene commits que tú no tienes. Siguiente paso: git pull. Git solo lo sabe después de un git fetch o git pull.

Divergida

Cada lado tiene commits que el otro no tiene. Siguiente paso: git pull --no-rebase (fusionar) o git pull --rebase.

Sin rama remota

Rama nueva que nunca subiste: git status no muestra ninguna línea «Your branch…». Siguiente paso: git push -u origin nombre-de-la-rama.

4. Estados especiales

Fusión a medias (conflicto)

Git no pudo combinar todo solo. Resuelve los archivos marcados «both modified» y cierra con git add + git commit; o cancela con git merge --abort. Ver la guía completa.

Conflicto resuelto, falta el commit

Ya no queda nada por resolver; la fusión se cierra con git commit.

HEAD desacoplado

No estás en ninguna rama. Vuelve con git switch -, o conserva lo hecho con git switch -c nueva-rama.

Pega tu git status y te lo explico

Entiende la salida en inglés de Git (la que imprime por defecto; verificada con Git 2.55). Todo ocurre en tu navegador: no se envía nada. Si tu Git está traducido y no lo reconozco, te lo digo en lugar de adivinar.

Individual, dentro de un equipo

El ciclo de trabajo diario

Este es el flujo que repetirás cada vez que te sientes a programar en tu carpeta. Sigue estas 4 etapas en orden:

0 de 5 pasos hechos hoy

  1. Etapa 1

    Arrancar a trabajar (Sincronizar)

    Paso 1Actualiza

    git pull
    Qué hace
    Siempre primero. Trae los cambios de tus compañeros para evitar conflictos.
    En simple
    Baja lo último de GitHub.
    Por qué
    La regla de oro es traer los últimos cambios antes de tocar nada. Te salva de conflictos.
  2. Etapa 2

    Programar y revisar

    Paso 2Revisa

    git status
    Qué hace
    Muestra qué archivos cambiaron (rojo = sin agregar, verde = agregado).
    En simple
    Mira qué archivos modificaste.
    Por qué
    Es tu radar. Te dice qué archivos están en rojo (modificados) y verde (listos).

    RecomendadoRevisa el detalle

    git diff
    Qué hace
    Muestra las líneas exactas que modificaste pero aún no agregaste (add).
    Por qué
    Muestra exactamente qué líneas borraste y agregaste antes de confirmar.
  3. Etapa 3

    Preparar y guardar (el commit)

    Paso 3Prepara

    git add .
    Qué hace
    Prepara los cambios para el guardado.
    En simple
    Agrega todo lo modificado al staging.
    Por qué
    El punto . significa "todo". Pasa archivos rojos a verde (staging area).
    Variante
    git add archivo.ext agrega solo ese archivo.

    Paso 4Guarda

    git commit -m "Descripción clara"
    Qué hace
    Guarda los cambios en tu historial local con una descripción.
    Por qué
    Saca archivos de la sala de espera y los guarda en el historial.
    Ejemplos
    "Agrego el header y los estilos del nav" · "Agrego la sección de contacto y sus estilos"
  4. Etapa 4

    Terminar la sesión (subir a la nube)

    Paso 5Sube

    git push
    Qué hace
    Sube tus commits a GitHub.
    En simple
    Envía tu trabajo a la nube.
    Por qué
    Sube tu foto (commit) a GitHub para que quede respaldada en la nube.
    Primer push de rama nueva
    git push -u origin nombre_rama

Machete: el flujo diario en un bloque

# 1. Arrancar a trabajar (Sincronizar)
git pull
# 2. Programar y revisar
git status
git diff
# 3. Preparar y guardar
git add .
git commit -m "Descripción clara"
# 4. Terminar la sesión (subir a la nube)
git push

Proceso grupal

Trabajo en equipo y ramas

Para trabajar en una funcionalidad sin afectar el código principal (main):

git branch

Lista las ramas (la actual tiene un *)

git checkout -b nueva_rama

Crea una rama nueva y te mueve a ella inmediatamente.

git switch nombre_rama

Te mueve a una rama que ya existe.

git merge nombre_rama

Fusiona los cambios de esa rama en la rama donde estás parado actualmente.

Los dos tipos de Merge que te vas a encontrar

1. Fast-Forward (Avance rápido)

Ocurre cuando intentas unir tu rama a main, pero nadie más ha subido cambios a main desde que te separaste. Git simplemente mueve la etiqueta de main hacia el frente hasta alcanzar tu último commit. Es limpio y automático.

2. Three-Way Merge (Fusión de tres vías)

Ocurre si tú estabas trabajando en tu rama y, al mismo tiempo, un compañero subió cambios a main. Como ambos caminos avanzaron por separado, Git analiza los dos historiales y crea automáticamente un nuevo commit especial (llamado Commit de Merge) que une ambas realidades.

El único peligro: Los conflictos de Merge (Merge Conflicts)

Git es extremadamente inteligente y sabe unir líneas de código de archivos diferentes de forma automática. Sin embargo, si tú y tu compañero modificaron exactamente la misma línea del mismo archivo, Git no sabe cuál de las dos versiones es la correcta.

En ese momento, Git detiene el proceso de merge, no rompe nada, y te dice: "Oye, decide tú con cuál versión nos quedamos". Una vez que eliges la línea ganadora en tu editor de código, el merge se completa.

Ahora llévalo a la práctica: el capítulo siguiente arma estos comandos en un flujo diario completo para el equipo, con el estado del repositorio en cada paso. Ir al flujo diario en equipo.

    Proceso de recuperación

    Historial y deshacer

    Para corregir errores sin perder el rastro:

    git log --oneline

    Muestra el historial de commits de forma resumida.

    git diff

    Muestra las líneas exactas que modificaste pero aún no agregaste (add).

    git restore archivo.html

    Descarta los cambios del archivo que aún no agregaste (add) y lo deja como en el último commit.

    ¡Cuidado, no se puede deshacer!

    git restore --staged archivo.html

    Saca un archivo del área de preparación (add), pero conserva tus ediciones.

    git revert ID_DEL_COMMIT

    Crea un nuevo commit que deshace los cambios de un commit anterior de forma segura.

    ¿Qué uso para deshacer?

    Depende de en qué punto está el cambio que quieres quitar:

    1. Lo editaste, pero no hiciste add

      git restore archivo.html

      Se pierde para siempre.

    2. Hiciste add, pero no commit

      git restore --staged archivo.html

      Vuelve a rojo; conserva lo que escribiste.

    3. Hiciste commit, pero no push

      git reset --soft HEAD~1

      Solo trabajo local. --hard destruye todos los cambios por completo.

    4. Ya lo subiste con push

      git revert ID_DEL_COMMIT

      Crea un commit nuevo; no destruye el historial. Es la forma segura en equipo.

    7

    Diagnóstico

    Resolución de errores frecuentes

    Busca el mensaje que te muestra la terminal: cada error trae su causa y su solución.

    fatal: not a git repository

    Causa
    No estás en la carpeta correcta.
    Solución
    Usa cd para entrar a la carpeta del proyecto o ejecuta git init. Ver cómo saber en qué carpeta estás.

    fatal: destination path '…' already exists and is not an empty directory.

    Causa
    Intentaste clonar en una carpeta que ya existe y tiene contenido: Git solo clona en una carpeta existente si está vacía.
    Solución
    Elige otro nombre (git clone URL otra-carpeta) o clona en una carpeta vacía.

    fatal: Not possible to fast-forward, aborting.

    Causa
    Usaste --ff-only pero las ramas divergieron: no se puede avanzar el puntero sin crear un commit de merge.
    Solución
    Quita --ff-only (Git creará el commit de merge) o usa git rebase. Ver los dos tipos de merge.

    (END) :

    Causa
    No es un error: la salida es más larga que la pantalla y Git la muestra con un paginador (por defecto less).
    Solución
    Presiona q para salir (con la barra espaciadora avanzas). Para no usar paginador: git --no-pager log.

    warning: in the working copy of '…', LF will be replaced by CRLF the next time Git touches it

    Causa
    Es un aviso, no un error: el comando se ejecutó. Windows termina las líneas con CR+LF y Linux/macOS solo con LF; Git convierte según core.autocrlf.
    Solución
    Puedes ignorarlo. Para fijar el comportamiento: git config --global core.autocrlf true en Windows o input en Linux/macOS.

    ! [rejected] (fetch first) ! [rejected] (non-fast-forward)

    Causa
    Alguien subió cambios antes que tú. Puntualmente: el remoto tiene commits de esa misma rama que tú no tienes. Con (fetch first) aún no los habías traído; con (non-fast-forward) ya los trajiste y tu rama quedó detrás de su par remoto.
    Solución
    Ejecuta git pull, resuelve si hay conflicto, y vuelve a hacer git push. (Si Git pide elegir cómo reconciliar: git pull --no-rebase.) Entiéndelo: dos personas en la misma rama.

    CONFLICT (content)

    Causa
    Dos personas tocaron las mismas líneas.
    Solución
    Abre el archivo, elige qué código queda, borra las marcas de conflicto (<<<<<<<, =======, >>>>>>>), luego git add y git commit. Ver la guía de 4 pasos.

    nothing to commit

    Causa
    No hay cambios nuevos para guardar.
    Solución
    Revisa con git status y asegúrate de haber hecho git add.

    error: Your local changes to the following files would be overwritten by merge

    Causa
    Tienes cambios sin guardar en archivos que el pull (o merge) también quiere modificar. Si tus cambios están en otros archivos, el pull funciona.
    Solución
    Guárdalos con git stash, haz el pull y recupéralos con git stash pop. Tus cambios no se pierden: el pull aborta («Aborting»). Ver la Fase 1 del flujo en equipo.

    fatal: Need to specify how to reconcile divergent branches.

    Causa
    Tu rama y la remota avanzaron por separado y Git no sabe si debe fusionarlas o rebasar tus commits.
    Solución
    Elige una vez: git pull --no-rebase (fusiona) o git pull --rebase. Para no repetirlo: git config --global pull.rebase false.

    fatal: The current branch … has no upstream branch.

    Causa
    Es una rama nueva: todavía no está enlazada con ninguna rama del remoto.
    Solución
    La primera vez usa git push -u origin nombre-de-la-rama. Después, git push alcanza.

    error: the branch '…' is not fully merged

    Causa
    Git no ve los commits de esa rama dentro de su rama remota ni de la actual (suele pasar tras un squash merge cuando la rama remota ya se borró).
    Solución
    Confirma en GitHub que el Pull Request está fusionado y recién entonces usa git branch -D rama, que fuerza el borrado.

    Si te equivocas

    Botiquín de emergencia

    No entres en pánico. Git está diseñado para salvarte. Usa estos comandos según tu error:

    Situación: Rompí un archivo, no hice add

    git restore archivo.html

    Descarta tus cambios y lo deja como en el último commit. No se puede deshacer.

    Situación: Hice git add por error

    git restore --staged archivo.html

    Saca de la preparación (vuelve a rojo) pero NO borra lo que escribiste.

    Situación: Quiero ver el historial

    git log --oneline

    Te lista todos tus commits con su ID.

    Más rescates del manual

    Situación: Hice un commit por error y todavía no lo subí

    git reset --soft HEAD~1

    Retrocede un commit y mantiene los archivos en staging. Nunca uses --hard en commits que ya subiste.

    Situación: Ya subí algo que estaba mal

    git revert ID_DEL_COMMIT

    Crea un nuevo commit que lo deshace sin destruir el historial. Busca el ID con git log --oneline.

    Situación: El merge salió mal

    git merge --abort

    Cancela el merge y vuelve al estado anterior.
